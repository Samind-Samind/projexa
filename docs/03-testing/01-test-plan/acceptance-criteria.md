## SCR-001 Dashboard ภาพรวม

- **Backlog:** [[../../01-requirements/backlog|backlog #001]] — MVP RAISE #1
- **อ้างอิง Spec:** [[../../01-requirements/01-spec/20260824-001-scr-001-dashboard-ภาพรวม|SCR-001]]
- **อ้างอิง Prototype:** ไม่มี prototype ณ วันที่เขียน

### AC-001-1 แสดงสรุปภาพรวมโครงการจากข้อมูลจริง

- **Given** ผู้ใช้ (PM) เข้าสู่ระบบและมีโครงการอยู่ในระบบแล้วอย่างน้อย 1 โครงการ
- **When** ผู้ใช้เปิดหน้า Dashboard ภาพรวม
- **Then** ระบบแสดงจำนวนโครงการและสถานะของแต่ละโครงการ โดยดึงจากข้อมูลจริงใน
  ระบบเท่านั้น ไม่ใช่ตัวเลขที่ AI สร้างขึ้นเอง
- อ้างอิง: Acceptance Criteria ข้อที่ 1 ในไฟล์ spec

### AC-001-2 แสดง % ความก้าวหน้าของแต่ละโครงการ

- **Given** โครงการมีข้อมูลความก้าวหน้าที่บันทึกไว้แล้ว (จาก SCR-016/SCR-017)
- **When** ผู้ใช้เปิดหน้า Dashboard ภาพรวม
- **Then** ระบบแสดง % ความก้าวหน้าของแต่ละโครงการ
- อ้างอิง: Acceptance Criteria ข้อที่ 2 ในไฟล์ spec

### AC-001-3 แสดงรายการงาน/หน้าจอที่ใกล้ครบกำหนด

- **Given** มีหน้าจอที่กำหนดวันครบกำหนดไว้และใกล้ถึงกำหนดนั้น
- **When** ผู้ใช้เปิดหน้า Dashboard ภาพรวม
- **Then** ระบบแสดงรายการงาน/หน้าจอที่ใกล้ครบกำหนดให้เห็นชัดเจน
- อ้างอิง: Acceptance Criteria ข้อที่ 3 ในไฟล์ spec

### AC-001-4 แสดงรายการงาน/หน้าจอที่เลยกำหนดแล้ว

- **Given** มีหน้าจอที่เลยวันครบกำหนดไปแล้วและยังไม่ปิดสถานะ
- **When** ผู้ใช้เปิดหน้า Dashboard ภาพรวม
- **Then** ระบบแสดงรายการงาน/หน้าจอที่เลยกำหนดแล้วแยกให้เห็นชัดเจน
- อ้างอิง: Acceptance Criteria ข้อที่ 4 ในไฟล์ spec

## SCR-002 รายการโครงการ

- **Backlog:** [[../../01-requirements/backlog|backlog #002]] — Phase 2
- **อ้างอิง Spec:** [[../../01-requirements/01-spec/20260824-002-scr-002-รายการโครงการ|SCR-002]]
- **อ้างอิง Prototype:** ไม่มี prototype ณ วันที่เขียน

### AC-002-1 ค้นหาโครงการตามชื่อ/ลูกค้า

- **Given** ผู้ใช้อยู่ที่หน้ารายการโครงการซึ่งมีหลายโครงการ
- **When** ผู้ใช้กรอกคำค้นหาที่ตรงกับชื่อโครงการหรือชื่อลูกค้า
- **Then** ระบบแสดงเฉพาะโครงการที่ชื่อหรือลูกค้าตรงกับคำค้นหา
- อ้างอิง: Acceptance Criteria ข้อที่ 1 ในไฟล์ spec

### AC-002-2 กรองรายการโครงการตามเงื่อนไข

- **Given** ผู้ใช้อยู่ที่หน้ารายการโครงการ
- **When** ผู้ใช้เลือกเงื่อนไขกรอง (เช่น สถานะโครงการ)
- **Then** ระบบแสดงเฉพาะโครงการที่ตรงกับเงื่อนไขที่เลือก
- อ้างอิง: Acceptance Criteria ข้อที่ 2 ในไฟล์ spec

### AC-002-3 แสดงผลแบบแบ่งหน้า

- **Given** จำนวนโครงการในระบบมากกว่าจำนวนที่แสดงได้ต่อหน้า
- **When** ผู้ใช้เปิดหน้ารายการโครงการ
- **Then** ระบบแสดงผลแบบแบ่งหน้า (pagination) และเปลี่ยนหน้าได้
- อ้างอิง: Acceptance Criteria ข้อที่ 3 ในไฟล์ spec

## SCR-003 ข้อมูลโครงการ

- **Backlog:** [[../../01-requirements/backlog|backlog #003]] — MVP RAISE #2
- **อ้างอิง Spec:** [[../../01-requirements/01-spec/20260824-003-scr-003-ข้อมูลโครงการ|SCR-003]]
- **อ้างอิง Prototype:** [SCR-003 prototype](../../02-design/01-prototypes/v1/scr-003.html)

### AC-003-1 เพิ่มโครงการใหม่พร้อมข้อมูลครบ

- **Given** ผู้ใช้ (PM) อยู่ที่หน้าข้อมูลโครงการในโหมดสร้างใหม่
- **When** ผู้ใช้กรอกชื่อโครงการ ลูกค้า ระยะเวลา งบประมาณ และทีมงาน ครบถ้วน
  แล้วกดบันทึก
- **Then** ระบบสร้างโครงการใหม่พร้อมข้อมูลทั้งหมดที่กรอก และแสดง toast
  ยืนยันว่าบันทึกสำเร็จ (ตามที่ prototype สาธิตปุ่ม "บันทึก")
- อ้างอิง: Acceptance Criteria ข้อที่ 1 ในไฟล์ spec

### AC-003-2 แก้ไขข้อมูลโครงการที่มีอยู่

- **Given** มีโครงการที่มีข้อมูลอยู่แล้วในระบบ
- **When** ผู้ใช้เปิดหน้าข้อมูลโครงการของโครงการนั้นและแก้ไขฟิลด์ (เช่น
  งบประมาณ) แล้วกดบันทึก
- **Then** ระบบบันทึกค่าที่แก้ไขใหม่ทับค่าเดิม และแสดงค่าใหม่เมื่อเปิดหน้านี้
  อีกครั้ง
- อ้างอิง: Acceptance Criteria ข้อที่ 2 ในไฟล์ spec

### AC-003-3 บันทึกการเปลี่ยนแปลงลง audit log

- **Given** ผู้ใช้แก้ไขข้อมูลโครงการ (เช่น งบประมาณจาก 900,000 เป็น 1,000,000
  บาท ตามที่ prototype สาธิตไว้)
- **When** ผู้ใช้บันทึกการเปลี่ยนแปลง
- **Then** ระบบบันทึกรายการลง audit log พร้อมวันที่/เวลา ผู้แก้ไข และ
  รายละเอียดการเปลี่ยนแปลง ตามหลัก Everything is Logged
- อ้างอิง: Acceptance Criteria ข้อที่ 3 ในไฟล์ spec

### AC-003-4 บังคับกรอกฟิลด์ที่จำเป็นก่อนบันทึก (suggested)

- **Given** ผู้ใช้อยู่ที่แบบฟอร์มข้อมูลโครงการ ซึ่ง prototype ระบุฟิลด์บังคับ
  (ชื่อโครงการ, ลูกค้า, วันที่เริ่มต้น, วันที่สิ้นสุด, งบประมาณ) ด้วยเครื่องหมาย `*`
- **When** ผู้ใช้กดบันทึกโดยเว้นฟิลด์บังคับข้อใดข้อหนึ่งไว้ว่าง
- **Then** ระบบต้องแจ้งเตือนและไม่บันทึกข้อมูลจนกว่าจะกรอกฟิลด์บังคับครบ
  (suggested — เป็นการขยายจากรายละเอียด UI ใน prototype ที่ spec ไม่ได้ระบุ
  ตรงๆ ต้องรอ BA/Tester ยืนยัน)
- อ้างอิง: (suggested) ขยายจาก prototype SCR-003 (เครื่องหมาย `*` ที่ label)

## SCR-004 นำเข้า/บันทึก TOR

- **Backlog:** [[../../01-requirements/backlog|backlog #004]] — MVP RAISE #3
- **อ้างอิง Spec:** [[../../01-requirements/01-spec/20260824-004-scr-004-นำเข้า-บันทึก-tor|SCR-004]]
- **อ้างอิง Prototype:** ไม่มี prototype ณ วันที่เขียน

### AC-004-1 อัปโหลดไฟล์ TOR ชนิด .docx/.pdf ที่มี text layer

- **Given** ผู้ใช้ (PM) มีไฟล์ TOR ชนิด .docx หรือ .pdf ที่มี text layer
- **When** ผู้ใช้อัปโหลดไฟล์ที่หน้านำเข้า/บันทึก TOR
- **Then** ระบบรับไฟล์และเริ่มกระบวนการสกัดข้อมูล
- อ้างอิง: Acceptance Criteria ข้อที่ 1 ในไฟล์ spec

### AC-004-2 กรอกเนื้อหา TOR เองได้กรณีไม่มีไฟล์

- **Given** ผู้ใช้ไม่มีไฟล์ TOR แต่มีเนื้อหา TOR อยู่ในมือ
- **When** ผู้ใช้เลือกโหมดกรอกเนื้อหาเองแล้วพิมพ์ข้อความ TOR ลงในระบบ
- **Then** ระบบรับเนื้อหาที่กรอกและใช้เป็นต้นทางสำหรับกระบวนการสกัดข้อมูล
  เช่นเดียวกับกรณีอัปโหลดไฟล์
- อ้างอิง: Acceptance Criteria ข้อที่ 2 ในไฟล์ spec

### AC-004-3 แสดงสถานะการสกัดของ AI

- **Given** ผู้ใช้เพิ่งอัปโหลดไฟล์ TOR หรือกรอกเนื้อหา TOR เสร็จ
- **When** ระบบเริ่มประมวลผลการสกัดด้วย AI (TOR Parser)
- **Then** ระบบแสดงสถานะปัจจุบันของการสกัดให้ผู้ใช้เห็น (กำลังประมวลผล /
  เสร็จแล้ว / ผิดพลาด) ตามสถานะจริงของกระบวนการ
- อ้างอิง: Acceptance Criteria ข้อที่ 3 ในไฟล์ spec

## SCR-005 ตรวจสอบผลสกัด TOR

- **Backlog:** [[../../01-requirements/backlog|backlog #005]] — MVP RAISE #4
- **อ้างอิง Spec:** [[../../01-requirements/01-spec/20260824-005-scr-005-ตรวจสอบผลสกัด-tor|SCR-005]]
- **อ้างอิง Prototype:** ไม่มี prototype ณ วันที่เขียน

### AC-005-1 แสดงผลลัพธ์ AI คู่กับข้อความต้นฉบับ

- **Given** ระบบสกัดข้อมูล TOR ด้วย AI เสร็จแล้ว
- **When** ผู้ใช้ (BA/PM) เปิดหน้าตรวจสอบผลสกัด TOR
- **Then** ระบบแสดงผลลัพธ์ที่ AI สกัดได้คู่กับข้อความต้นฉบับของ TOR ในตำแหน่ง
  ที่เทียบกันได้
- อ้างอิง: Acceptance Criteria ข้อที่ 1 ในไฟล์ spec

### AC-005-2a ยืนยันรายการที่ AI สกัด

- **Given** มีรายการที่ AI สกัดแสดงอยู่ในหน้าตรวจสอบ
- **When** ผู้ใช้ (BA/PM) กดยืนยันรายการนั้นทีละข้อ
- **Then** รายการนั้นเปลี่ยนป้ายจาก `AI Generated` เป็น `Human Confirmed`
- อ้างอิง: Acceptance Criteria ข้อที่ 2 ในไฟล์ spec

### AC-005-2b แก้ไข เพิ่ม หรือลบรายการที่ AI สกัด

- **Given** มีรายการที่ AI สกัดแสดงอยู่ในหน้าตรวจสอบซึ่งไม่ถูกต้องครบถ้วน
- **When** ผู้ใช้ (BA/PM) แก้ไขข้อความของรายการ หรือเพิ่มรายการใหม่ หรือลบ
  รายการที่ไม่ถูกต้องออก
- **Then** ระบบบันทึกการแก้ไข/เพิ่ม/ลบนั้นไว้ และรายการที่ผลลัพธ์แสดงตรงกับ
  ที่ผู้ใช้แก้ไขล่าสุด
- อ้างอิง: Acceptance Criteria ข้อที่ 2 ในไฟล์ spec

### AC-005-3 ไม่มีข้อมูลถูกบันทึกจนกว่าจะยืนยัน (Human-in-the-loop)

- **Given** มีรายการที่ AI สกัดแต่ยังไม่ถูกยืนยันโดยผู้ใช้
- **When** ผู้ใช้ปิดหน้าหรือยังไม่กดยืนยัน
- **Then** รายการนั้นต้องไม่ถูกบันทึกเป็นทางการเข้า SCR-006 (ทะเบียน REQ)
  จนกว่าจะผ่านการยืนยันจากคน
- อ้างอิง: Acceptance Criteria ข้อที่ 3 ในไฟล์ spec

### AC-005-4 รายการที่อ้างอิงต้นทางไม่ได้ต้องติดป้าย suggested

- **Given** มีรายการที่ AI สกัดแต่ไม่สามารถระบุ `source_clause` อ้างอิงกลับไป
  ยังข้อความต้นฉบับได้
- **When** ผู้ใช้เปิดหน้าตรวจสอบผลสกัด TOR
- **Then** รายการนั้นต้องติดป้าย `suggested` แยกให้ผู้ใช้พิจารณาต่างหากจาก
  รายการที่มีต้นทางชัดเจน
- อ้างอิง: Acceptance Criteria ข้อที่ 4 ในไฟล์ spec

## SCR-006 ทะเบียนความต้องการ (REQ)

- **Backlog:** [[../../01-requirements/backlog|backlog #006]] — MVP RAISE #5
- **อ้างอิง Spec:** [[../../01-requirements/01-spec/20260824-006-scr-006-ทะเบียนความต้องการ-req|SCR-006]]
- **อ้างอิง Prototype:** ไม่มี prototype ณ วันที่เขียน

### AC-006-1 แสดงรายการ REQ แบบ list และ detail

- **Given** มี Requirement ที่ยืนยันแล้วจาก SCR-005 อยู่ในระบบ
- **When** ผู้ใช้ (BA) เปิดหน้าทะเบียนความต้องการ
- **Then** ระบบแสดงรายการ REQ แบบ list และเปิดดูรายละเอียด (detail) ของแต่ละ
  REQ ได้
- อ้างอิง: Acceptance Criteria ข้อที่ 1 ในไฟล์ spec

### AC-006-2 แยกประเภท Functional (FR) และ Non-Functional (NFR)

- **Given** มี REQ ทั้งประเภท Functional และ Non-Functional อยู่ในทะเบียน
- **When** ผู้ใช้เปิดหน้าทะเบียนความต้องการ
- **Then** ระบบแสดง/กรองแยกประเภท FR และ NFR ให้เห็นชัดเจน
- อ้างอิง: Acceptance Criteria ข้อที่ 2 ในไฟล์ spec

### AC-006-3 REQ ลิงก์กลับไปยังข้อ (clause) ใน TOR ต้นทางได้

- **Given** REQ นั้นถูกสกัดมาจากข้อความใน TOR ที่ระบุ clause ชัดเจน
- **When** ผู้ใช้เปิดดูรายละเอียดของ REQ นั้น
- **Then** ระบบแสดงลิงก์ย้อนกลับไปยังข้อ (clause) ใน TOR ต้นทางได้
- อ้างอิง: Acceptance Criteria ข้อที่ 3 ในไฟล์ spec

## SCR-007 งวดงานและเอกสารส่งมอบ

- **Backlog:** [[../../01-requirements/backlog|backlog #007]] — MVP RAISE #6
- **อ้างอิง Spec:** [[../../01-requirements/01-spec/20260824-007-scr-007-งวดงานและเอกสารส่งมอบ|SCR-007]]
- **อ้างอิง Prototype:** ไม่มี prototype ณ วันที่เขียน

### AC-007-1 กำหนดงวดงาน (Milestone) พร้อมวันครบกำหนด

- **Given** ผู้ใช้ (PM) อยู่ที่หน้างวดงานและเอกสารส่งมอบของโครงการ
- **When** ผู้ใช้เพิ่มงวดงานใหม่พร้อมระบุวันครบกำหนด
- **Then** ระบบบันทึกงวดงานพร้อมวันครบกำหนดนั้นไว้กับโครงการ
- อ้างอิง: Acceptance Criteria ข้อที่ 1 ในไฟล์ spec

### AC-007-2 ระบุเอกสารที่ต้องส่งมอบในแต่ละงวด

- **Given** มีงวดงานที่สร้างไว้แล้วอย่างน้อย 1 งวด
- **When** ผู้ใช้เลือกประเภทเอกสารที่ต้องส่งมอบ (REQ/SDD/TSC/User Manual) ให้
  กับงวดงานนั้น
- **Then** ระบบบันทึกความสัมพันธ์ระหว่างงวดงานกับประเภทเอกสารที่ต้องส่งมอบ
- อ้างอิง: Acceptance Criteria ข้อที่ 2 ในไฟล์ spec

### AC-007-3 แสดง % การชำระเงินที่ผูกกับงวดงาน

- **Given** งวดงานนั้นมีการระบุ % การชำระเงินไว้
- **When** ผู้ใช้เปิดดูรายละเอียดของงวดงาน
- **Then** ระบบแสดง % การชำระเงินที่ผูกกับงวดงานนั้น

## SCR-017 ประวัติการเปลี่ยนแปลง

- **When** ผู้ใช้เปิดหน้าประวัติการเปลี่ยนแปลงและเลื่อนดูรายการเก่าที่สุด
- **Then** ระบบแสดงประวัติทั้งหมดย้อนหลังได้โดยไม่มีข้อมูลถูกลบทิ้ง

## SCR-018 ติดตามปัญหา (Issue)

### AC-018-1 บันทึกปัญหา (Issue) พร้อมผลกระทบและแนวทางแก้ไข

- **Given** ผู้ใช้ (ทีม/Tester) พบปัญหาระหว่างการทำงาน
- **When** ผู้ใช้บันทึก Issue ใหม่พร้อมระบุผลกระทบและแนวทางแก้ไข
- **Then** ระบบบันทึก Issue นั้นพร้อมรายละเอียดผลกระทบและแนวทางแก้ไขที่กรอก

- **Given** มี Issue ที่บันทึกไว้แล้วและยังไม่ได้กำหนดผู้รับผิดชอบ
- **When** ผู้ใช้กำหนดผู้รับผิดชอบให้ Issue นั้นและเปลี่ยนสถานะตามความคืบหน้า
- **Then** ระบบบันทึกผู้รับผิดชอบและสถานะปัจจุบันของ Issue
- อ้างอิง: Acceptance Criteria ข้อที่ 2 ในไฟล์ spec

### AC-018-3 ผูก Issue กับหน้าจอหรือโครงการที่เกี่ยวข้องได้

- **Given** Issue นั้นเกี่ยวข้องกับหน้าจอใดหน้าจอหนึ่งของโครงการ
- **When** ผู้ใช้ผูก Issue นั้นเข้ากับหน้าจอที่เกี่ยวข้อง
- **Then** ระบบบันทึกความสัมพันธ์ระหว่าง Issue กับหน้าจอ/โครงการนั้น
- อ้างอิง: Acceptance Criteria ข้อที่ 3 ในไฟล์ spec

- **อ้างอิง Spec:** [[../../01-requirements/01-spec/20260824-024-scr-024-ประวัติเวอร์ชันเอกสาร|SCR-024]]
- **อ้างอิง Prototype:** ไม่มี prototype ณ วันที่เขียน

### AC-024-1 เก็บเอกสารทุกเวอร์ชันที่เคยสร้าง

- **Given** ผู้ใช้ export เอกสารประเภทเดียวกันจากงวดงานเดียวกันมากกว่า 1 ครั้ง
  (SCR-023)
- **When** ผู้ใช้เปิดหน้าประวัติเวอร์ชันเอกสาร
- **Then** ระบบแสดงทุกเวอร์ชันที่เคยสร้างไว้ ไม่มีเวอร์ชันใดถูกทับหรือหาย
- อ้างอิง: Acceptance Criteria ข้อที่ 1 ในไฟล์ spec

### AC-024-2 เทียบความต่างระหว่างเวอร์ชันได้

- **Given** เอกสารนั้นมีอย่างน้อย 2 เวอร์ชัน
- **When** ผู้ใช้เลือก 2 เวอร์ชันเพื่อเทียบความต่าง
- **Then** ระบบแสดงความแตกต่างระหว่าง 2 เวอร์ชันนั้นให้ผู้ใช้เห็น
- อ้างอิง: Acceptance Criteria ข้อที่ 2 ในไฟล์ spec

### AC-024-3 ดาวน์โหลดเอกสารเวอร์ชันย้อนหลังได้

- **Given** มีเวอร์ชันเก่าของเอกสารเก็บไว้ในระบบ
- **When** ผู้ใช้เลือกดาวน์โหลดเวอร์ชันเก่านั้น
- **Then** ระบบส่งไฟล์เอกสารของเวอร์ชันที่เลือกให้ผู้ใช้ดาวน์โหลดได้ครบถ้วน
- อ้างอิง: Acceptance Criteria ข้อที่ 3 ในไฟล์ spec

## SCR-025 ผู้ใช้งานและสิทธิ์

- **Backlog:** [[../../01-requirements/backlog|backlog #025]] — Phase 2
- **อ้างอิง Spec:** [[../../01-requirements/01-spec/20260824-025-scr-025-ผู้ใช้งานและสิทธิ์|SCR-025]]
- **อ้างอิง Prototype:** ไม่มี prototype ณ วันที่เขียน

### AC-025-1 เพิ่ม/แก้ไข/ลบผู้ใช้งานในระบบได้

- **Given** ผู้ใช้ (Admin) เปิดหน้าผู้ใช้งานและสิทธิ์
- **When** ผู้ใช้เพิ่มผู้ใช้งานใหม่ หรือแก้ไข หรือลบผู้ใช้งานที่มีอยู่
- **Then** ระบบบันทึกการเพิ่ม/แก้ไข/ลบผู้ใช้งานนั้นสำเร็จ
- อ้างอิง: Acceptance Criteria ข้อที่ 1 ในไฟล์ spec

### AC-025-2 กำหนด Role (PM/SA/BA/Dev/Tester/Viewer/Admin) ให้ผู้ใช้ได้ในระดับโครงการ

- **Given** มีผู้ใช้งานอยู่ในระบบแล้ว
- **When** ผู้ใช้ (Admin) กำหนด Role ให้ผู้ใช้งานนั้นในระดับโครงการหนึ่ง
- **Then** ระบบบันทึก Role ของผู้ใช้งานนั้นในโครงการที่กำหนด
- อ้างอิง: Acceptance Criteria ข้อที่ 2 ในไฟล์ spec

### AC-025-3 หนึ่งผู้ใช้มีได้หลาย Role

- **Given** ผู้ใช้งานคนหนึ่งได้รับมอบหมาย Role อยู่แล้ว 1 บทบาท
- **When** ผู้ใช้ (Admin) เพิ่ม Role ที่สองให้กับผู้ใช้งานคนเดียวกัน
- **Then** ระบบบันทึกให้ผู้ใช้งานคนนั้นมีทั้งสอง Role พร้อมกันได้ ตามที่ระบุ
  ใน §2
- อ้างอิง: Acceptance Criteria ข้อที่ 3 ในไฟล์ spec

## SCR-026 ข้อมูลตั้งต้น

- **Backlog:** [[../../01-requirements/backlog|backlog #026]] — Phase 2
- **อ้างอิง Spec:** [[../../01-requirements/01-spec/20260824-026-scr-026-ข้อมูลตั้งต้น|SCR-026]]
- **อ้างอิง Prototype:** ไม่มี prototype ณ วันที่เขียน

### AC-026-1 จัดการข้อมูลตั้งต้น (master data)

- **Given** ผู้ใช้ (Admin) เปิดหน้าข้อมูลตั้งต้น
- **When** ผู้ใช้เพิ่ม/แก้ไข/ลบข้อมูลตั้งต้น (ประเภทเอกสาร ประเภทหน้าจอ
  สถานะ ตำแหน่งงาน)
- **Then** ระบบบันทึกการเปลี่ยนแปลงข้อมูลตั้งต้นนั้นสำเร็จ
- อ้างอิง: Acceptance Criteria ข้อที่ 1 ในไฟล์ spec

### AC-026-2 ข้อมูลตั้งต้นถูกดึงไปใช้ในหน้าจออื่นทั่วทั้งระบบ

- **Given** มีการเพิ่มค่าข้อมูลตั้งต้นใหม่ (เช่น ตำแหน่งงานใหม่) ที่หน้านี้
- **When** ผู้ใช้เปิดหน้าจออื่นที่ต้องเลือกค่าจากชุดข้อมูลตั้งต้นนั้น (เช่น
  SCR-013 มอบหมายผู้รับผิดชอบ)
- **Then** ค่าข้อมูลตั้งต้นใหม่ที่เพิ่มไว้ต้องปรากฏให้เลือกใช้ได้จริงในหน้า
  จออื่นนั้น ตามหลัก Single Source of Truth
- อ้างอิง: Acceptance Criteria ข้อที่ 2 ในไฟล์ spec
