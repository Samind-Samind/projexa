# High-Level Architecture (Conceptual)

Skill นี้คุมขั้นตอนออกแบบและจัดทำ **เอกสารสถาปัตยกรรมระดับสูงเชิงแนวคิด** ของ
โปรเจกต์ Projexa ที่ `docs/02-design/02-technical/architecture.md` — อธิบายว่า
ระบบประกอบด้วยส่วนใดบ้าง แต่ละส่วนรับผิดชอบอะไร ข้อมูลไหลผ่านส่วนต่างๆ
อย่างไรตาม user journey จริง และขอบเขต/กติกาเชิงแนวคิดที่ทุกองค์ประกอบต้องยึด
**เอกสารนี้ต้องไม่อ้างอิงเทคโนโลยี/framework/ผลิตภัณฑ์เฉพาะเจาะจงใดๆ** (เช่น
ห้ามเขียนว่า "ใช้ PostgreSQL" หรือ "ใช้ React") — เรื่องนั้นเป็นหน้าที่ของ
เอกสาร `docs/02-design/02-technical/tech-stack.md` (skill `tech-stack`) ซึ่ง
ควรออกแบบให้สอดคล้องกับเอกสารนี้ทีหลัง ไม่ใช่ก่อน

ตามหลัก **Human-in-the-loop** ของ Projexa: การตัดสินใจเชิงโครงสร้าง (แบ่ง
component อย่างไร, boundary อยู่ตรงไหน, ข้อมูลไหลแบบไหน) ต้องมาจาก user
ยืนยันเสมอ ห้ามเดาแทนเมื่อไม่ชัดเจน — ต้องถามพร้อมแนวทางให้เลือกอย่างน้อย 3
ทาง แต่ละทางต้องมีข้อดี-ข้อเสียกำกับ เพื่อให้ user พิจารณาได้จริง

**สำคัญ:** ทำขั้นตอนที่ 1–9 ด้านล่างเองใน main loop (ห้ามส่งให้ sub agent ทำ)
เพราะต้องสัมภาษณ์-ออกแบบ-ขอยืนยันกับ user แบบ interactive ส่วน "การเขียนไฟล์
จริง" ให้มอบหมายให้ sub agent ชื่อ `architecture-writer` ผ่าน Agent tool เมื่อ
ทุกอย่างถูกออกแบบและยืนยันแล้วเท่านั้น sub agent ตัวนี้ทำงานแบบ one-shot และ
ถามคำถามกลับ user ไม่ได้ — **ห้ามให้ sub agent ตัดสินใจโครงสร้างสถาปัตยกรรม
หรือเลือกทางเลือกเอง** หน้าที่นั้นเป็นของขั้นตอนในสกิลนี้เท่านั้น

## ขั้นตอน

### 1. รับสโคป

ถ้า user ระบุมาแล้ว (เช่น "ทำ data flow ของขั้นตอนนำเข้า TOR ใหม่", "ปรับ
component breakdown ใหม่") ให้ resolve เป็นสโคปที่ต้องทำ ถ้า **ไม่ได้ระบุ**
ให้ถามด้วย `AskUserQuestion` อย่างน้อย 3 ตัวเลือก เช่น:

- ตัวเลือก 1: สร้าง/ทบทวนเอกสารทั้งฉบับ (ทุก section) — ข้อดี: ได้ภาพรวมที่
  สอดคล้องกันทั้งระบบตั้งแต่ต้น ข้อเสีย: ใช้เวลาสัมภาษณ์นานกว่า
- ตัวเลือก 2: เฉพาะ section ที่ยังไม่เคยถูกยืนยัน (Draft/ยังไม่มี) — ข้อดี:
  เร็ว ไม่ถามซ้ำสิ่งที่ยืนยันแล้ว ข้อเสีย: อาจไม่สอดคล้องกับ section ที่
  Confirmed ไปแล้วถ้าบริบทเปลี่ยนมาก
- ตัวเลือก 3: ระบุเจาะจง section/data flow เอง (พิมพ์ชื่อ)

### 2. ตรวจเอกสาร architecture.md เดิม

`Glob`/`Read` `docs/02-design/02-technical/architecture.md` ถ้ามีอยู่แล้ว:
อ่านเพื่อรู้ว่า section ไหน**สถานะ Confirmed**แล้ว (มีวันที่ยืนยัน) กับ
section ไหนยัง `Draft (suggested)`/ยังไม่มี — ใช้กำหนดว่าขั้นตอน 5 ต้องถามอะไร
เพิ่ม **ห้ามถามซ้ำสิ่งที่ Confirmed แล้ว** เว้นแต่ user เลือกตัวเลือก 1 ใน
ขั้นตอน 1 (ทบทวนทั้งฉบับ) โดยชัดเจน

ถ้าในบทสนทนานี้เอง**มีข้อมูล/ผลออกแบบอยู่แล้ว** ให้ใช้ข้อมูลเดิมได้เลยไม่ต้อง
สัมภาษณ์ซ้ำ ถามเฉพาะส่วนที่ยังขาดหรือยังไม่ชัดพอจะเขียนเป็นเอกสารทางการได้

### 4. สรุปข้อเท็จจริง vs ช่องว่างที่ต้องถาม

รวบรวมจากขั้นตอน 3 แล้วแยกให้ชัดว่า **มีข้อมูลจริงจากเอกสารแล้ว** หรือ **NOT
DOCUMENTED** (ห้ามเดาแทนช่องที่ไม่มีข้อมูล) หัวข้อที่ต้องเช็คเสมอ (เฉพาะที่
เกี่ยวกับสโคป):

- System boundary: actor/ระบบภายนอกที่ต้อง integrate ด้วยจริง (เช่น ระบบ
  SSO/authentication ขององค์กร, ช่องทางแจ้งเตือนภายนอก, ระบบเดิมที่ต้อง
  migrate ข้อมูลเข้ามา) — เกินกว่าที่ระบุใน §10 หรือไม่
- หลักการแบ่ง component/layer เชิงแนวคิด: ควรยึดตาม 4 layer เดิมใน §3 (
  Presentation / Application / AI Orchestration / Data) หรือปรับใหม่, ควรแบ่ง
  component ภายใน Application Layer ตาม M1–M7 ตรงๆ หรือจัดกลุ่มต่างไป
- ขอบเขต multi-tenancy/multi-project: ระบบรองรับหลายโครงการพร้อมกันแบบแยก
  ขอบเขตข้อมูลกันชัดเจนแค่ไหน (เชิงแนวคิด ไม่ใช่ระดับ schema จริง)
- แนวทาง security/RBAC เชิงแนวคิด: มีกี่ระดับบทบาท เข้าถึงข้อมูลระดับใดได้
  บ้าง (อ้างอิง §2 ผู้ใช้งานและสิทธิ์ ถ้ามีข้อมูลอยู่แล้ว)
- แนวทาง audit/versioning เชิงแนวคิด: ทุก state change ต้องเก็บ audit log
  แบบ event เดี่ยวๆ หรือ snapshot เป็นช่วง (เชื่อมกับ `StatusHistory`/audit
  trail ใน §4.2)
- ความสัมพันธ์ระหว่าง AI Orchestration กับ Human-in-the-loop gate: จุดไหนบ้าง
  ที่ต้องมี "gate" ให้คนยืนยันก่อนข้อมูลไหลต่อ (อ้างอิง gate ใน
  `user-journey.md` ถ้ามี)
- resilience เชิงแนวคิด: ถ้า AI Orchestration ล้มเหลว/ให้ผลไม่ครบ ระบบควร
  behave อย่างไรในระดับแนวคิด (เช่น block ต่อ vs อนุญาตกรอกมือแทน)
- ลำดับความสำคัญ non-functional เชิงแนวคิด (เช่น ความสอดคล้องของข้อมูล
  traceability สำคัญกว่าความเร็วตอบสนองหรือไม่) ที่จะมีผลต่อการออกแบบ boundary

### 5. สัมภาษณ์ผู้ใช้แบบเข้มข้น

สำหรับทุกหัวข้อในขั้นตอน 4 ที่เป็น **NOT DOCUMENTED** และเกี่ยวกับสโคป **ต้อง
ถามด้วย `AskUserQuestion`** แบ่งเป็นชุดละไม่เกิน 4 คำถามต่อการเรียก 1 ครั้ง
(เรียกได้หลายรอบจนครบ) **ทุกคำถามต้องมีตัวเลือกอย่างน้อย 3 แนวทางเสมอ พร้อม
ข้อดี-ข้อเสียของแต่ละตัวเลือกในคำอธิบาย** (ไม่ใช่แค่ yes/no) ตัวอย่างรูปแบบ:

> "Application Layer ควรแบ่ง component ภายในอย่างไร (เชิงแนวคิด ไม่ใช่ชื่อ
> service จริง)?"
> - ตัวเลือก 1: แบ่งตาม 4 service เดิมใน §3 (Project/Analysis/Tracking/
>   Document Generator) — ข้อดี: สอดคล้องกับเอกสารเดิม เปลี่ยนแปลงน้อย ข้อเสีย:
>   อาจไม่ครอบคลุมความรับผิดชอบใหม่ที่เพิ่มมาใน backlog
> - ตัวเลือก 2: แบ่งตาม 7 โมดูล M1–M7 ตรงๆ — ข้อดี: สาวกลับไปยังหน้าจอ/
>   requirement ได้ตรงที่สุด ข้อเสีย: component ละเอียดเกินระดับ "high-level"
> - ตัวเลือก 3: แบ่งตาม bounded context เชิงธุรกิจ (เช่น TOR & Requirement,
>   Planning & Tracking, Testing & Quality, Document Delivery) — ข้อดี:
>   สะท้อนขอบเขตความรับผิดชอบทางธุรกิจ พร้อมขยายเป็น service จริงทีหลังได้ง่าย
>   ข้อเสีย: ต้อง map กลับไปยัง M1–M7 เพิ่มอีกชั้นหนึ่ง

ถ้า user ตอบแบบเปิดกว้าง/มอบให้ AI ตัดสินใจแทน (เช่น "ช่วยคิดให้หน่อย", "ให้ AI
ประเมินเอง") ให้บันทึกไว้ว่าเป็น**มติที่ user มอบอำนาจให้ประเมินแทน** (ไม่ใช่
ข้อมูลจริงจาก user) แล้วเลือกแนวทางที่เหมาะสมที่สุดพร้อมเหตุผล แต่ต้องระบุป้าย
`(ประเมินแทนโดย AI ตามที่ user มอบอำนาจ)` กำกับไว้ในเอกสารเสมอ — ไม่ใช่การเดา
แบบไม่มีที่มา

ถามได้หลายรอบจนกว่าจะเก็บข้อมูลครบพอจะออกแบบได้อย่างสมเหตุสมผล ไม่ต้องรีบสรุป
ถ้ายังมีความกำกวมสำคัญเหลืออยู่

### 6. ร่างเนื้อหาสถาปัตยกรรมเชิง conceptual

สังเคราะห์จากขั้นตอน 3 และ 5 เป็นร่างเอกสาร (แสดงให้ user เห็นในแชทก่อนเขียน
ไฟล์จริงเสมอ — ดูขั้นตอน 7) ประกอบด้วย:

- **System boundary / Context diagram**: actor ภายใน (Role ตาม §2) + ระบบ/
  actor ภายนอกที่ยืนยันจากขั้นตอน 5 วาดเป็น ASCII diagram หรือ mermaid
  `flowchart` — ระบุเฉพาะ "อะไรคุยกับอะไร" ห้ามระบุ protocol/tech เฉพาะเจาะจง
- **Component/Layer breakdown**: ต่อ component หนึ่ง ระบุ หน้าที่รับผิดชอบ,
  ขอบเขต (อะไรอยู่ใน/นอกความรับผิดชอบ), ความสัมพันธ์กับ M1–M7/entity ใน §4,
  สถานะ (`Confirmed`/`Draft (suggested)`)
- **Data flow ตาม User Journey**: หยิบ flow หลักจาก
  `docs/02-design/01-prototypes/user-journey.md` มาแปลงเป็น data flow เชิง
  concept (ไม่ใช่ UI flow ซ้ำของเดิม) แสดงว่าข้อมูลอะไรถูกสร้าง/แปลง/ยืนยัน/
  ส่งต่อระหว่าง component ไหนบ้าง ระบุจุด human-in-the-loop gate ให้ชัดเจน ทำ
  เป็น mermaid `sequenceDiagram` หรือ `flowchart` อย่างน้อย 1 diagram ต่อ flow
  หลัก (เช่น TOR import → extraction → confirm → requirement, design analysis
  → screen confirm, document generation)
- **ขอบเขต AI Orchestration**: อธิบายกติกาจาก §7–§8 ในระดับ conceptual (AI
  คืนค่า structured data เท่านั้น, แยกจาก Document Generator เด็ดขาด, ทุกผลลัพธ์
  ต้องผ่าน human confirm ก่อนเข้าเป็นข้อมูลจริง) — ไม่ระบุชื่อโมเดล/API
  เฉพาะเจาะจง
- **Cross-cutting concerns**: audit/traceability enforcement เชิงแนวคิด (เส้น
  `TorClause → Requirement → Screen → TestCase → TestResult` ต้องคง integrity
  ได้ที่ระดับไหน), security/RBAC เชิงแนวคิด, resilience เชิงแนวคิดจากขั้นตอน 5
- **เทียบกับ §3 เดิม**: ระบุว่าโครงสร้างที่ออกแบบใหม่ **เหมือนหรือต่าง**กับ
  โครงร่าง 4 layer ใน §3 พร้อมเหตุผล ถ้าต่างกัน ต้องเสนอแนวทางอย่างน้อย 3 ทาง
  ให้ user เลือกว่าจะจัดการความต่างนี้อย่างไร (เช่น ยึดผลออกแบบใหม่/คงของเดิม/
  รอข้อมูลเพิ่มก่อนตัดสิน) — เตรียมไว้ใช้ในขั้นตอน 8

### 7. แสดงผลให้ user รีวิวก่อนเขียนไฟล์เสมอ

**ห้ามเรียก sub agent ก่อนขั้นตอนนี้เด็ดขาด** แสดง diagram + component
breakdown + data flow + คำแนะนำของทุก section ในสโคปให้ user เห็นในแชทก่อน
แล้วขอให้ user ยืนยันการตัดสินใจต่อ section อย่างชัดเจน (เช่น "ยืนยันตามที่
ออกแบบ" หรือ "เลือกแนวทางอื่นแทน" หรือ "ขอข้อมูลเพิ่มก่อนตัดสิน") — section ที่
user ยังไม่ยืนยัน ให้คงสถานะ `Draft (suggested)` ในเอกสาร ไม่ใช่ `Confirmed`

ถ้ามี section ที่ผลออกแบบรอบนี้ต่างจากโครงร่าง §3 เดิม **ต้องถาม**ด้วย
`AskUserQuestion` อย่างน้อย 3 ตัวเลือก เช่น:

- ตัวเลือก 1: แก้ diagram §3 ให้ตรงกับผลออกแบบใหม่ + ใส่ note อ้างอิงไปที่
  `architecture.md` เป็น source of truth — ข้อดี: ไม่มีข้อมูลขัดแย้งกันใน
  repo ข้อเสีย: ต้องแก้เอกสารหลักของระบบ
- ตัวเลือก 2: ไม่แก้ §3 ให้ `architecture.md` เป็นเอกสารล่าสุดเพียงจุดเดียว
  พร้อมลิงก์ไขว้ทั้งสองทาง — ข้อดี: ไม่กระทบเอกสารหลัก ข้อเสีย: มีข้อมูล 2
  เวอร์ชันอยู่ใน repo ต้องดูวันที่ให้ดี
- ตัวเลือก 3: ยังไม่ตัดสินใจตอนนี้ รอ SA/PM ยืนยันเป็นทางการก่อนค่อย sync

### 9. สรุปแผนให้ user ยืนยันครั้งสุดท้าย

สรุปสั้นๆ ว่าจะสร้าง/แก้ไฟล์อะไรบ้าง (สร้างใหม่/แก้ section ใดใน
`architecture.md`, จะแก้ §3 หรือไม่) แล้วขอยืนยันหนึ่งครั้งก่อนเรียก sub agent
เพราะเป็นการสร้าง/แก้ไฟล์จริงในโปรเจกต์

### 10. มอบหมายให้ sub agent `architecture-writer`

เมื่อ user ยืนยันแล้ว เรียกผ่าน Agent tool (subagent_type:
`architecture-writer`) พร้อมข้อมูลทั้งหมดที่จำเป็นในพรอมป์ (ทุกอย่างต้อง
finalize แล้ว ห้ามส่งให้ sub agent ไปคิดต่อเอง):

- วันที่ปัจจุบัน (`YYYYMMDD` และ `YYYY-MM-DD`) จาก context ของ session
- โหมด: "สร้างใหม่ทั้งไฟล์" หรือ "แก้/เพิ่ม section: {รายชื่อ}"
- Context diagram ที่ finalize แล้ว (ASCII หรือ mermaid source)
- ต่อแต่ละ component: หน้าที่, ขอบเขต, ความสัมพันธ์กับ M1–M7/entity, สถานะ
  (`Confirmed` พร้อมวันที่ / `Draft (suggested)`)
- Data flow diagram(s) ที่ finalize แล้ว (mermaid source) พร้อมชื่อ flow และ
  อ้างอิง user-journey.md ที่ตรงกัน
- เนื้อหาขอบเขต AI Orchestration และ cross-cutting concerns ที่ finalize แล้ว
- ผลเทียบกับ §3 เดิม (เหมือน/ต่าง + เหตุผล)
- มติเรื่อง sync §3 จากขั้นตอน 8 (sync / ไม่ sync / รอ) — ถ้า sync ต้องระบุ
  diagram/เนื้อหาใหม่ที่จะแทนที่ §3 ให้ชัด

sub agent จะจัดการให้ครบ: เขียน/แก้
`docs/02-design/02-technical/architecture.md`, อัปเดต
`docs/02-design/02-technical/index.md`, แก้ §3 ของ
`Projexa-System-Design-R1.md` เฉพาะกรณีมีมติให้ sync, และบันทึก `docs/05-log/`

### 11. รายงานผลกลับ user

สรุป path ไฟล์ที่ถูกสร้าง/แก้ไขทั้งหมด, section ไหน `Confirmed` แล้วบ้าง,
section ไหนยัง `Draft (suggested)` รอข้อมูล/การยืนยันเพิ่ม, และย้ำว่าเอกสารนี้
ยังเป็นระดับ conceptual — การเลือกเทคโนโลยีจริงให้ใช้ skill `tech-stack`
ต่อ พร้อมย้ำว่าต้องรอ SA/PM ยืนยันเป็นทางการตามหลัก Human-in-the-loop ก่อนถือ
เป็นมติสุดท้ายของทีม

## สิ่งที่ห้ามทำ

- ห้ามให้ sub agent ตัดสินใจโครงสร้าง component, data flow, หรือทางเลือก
  ออกแบบเอง — ทุกอย่างต้องออกแบบและยืนยันโดย user ผ่าน main loop นี้ก่อน
  แล้วส่งเป็นค่าที่ finalize แล้วเท่านั้น
- ห้ามอ้างอิงเทคโนโลยี/framework/ผลิตภัณฑ์เฉพาะเจาะจงในเอกสารนี้เด็ดขาด (เช่น
  ชื่อ database, ภาษาโปรแกรม, cloud provider) แม้จะมีข้อมูลจาก `tech-stack.md`
  อยู่แล้วก็ตาม — ถ้า user พยายามใส่รายละเอียดเทคโนโลยีเข้ามา ให้แจ้งว่าควรไป
  ที่ skill `tech-stack` แทน
- ห้ามเดาคำตอบแทน user เมื่อเอกสารโปรเจกต์ไม่มีข้อมูล (`NOT DOCUMENTED`) —
  ต้องถามเสมอ ยกเว้น user มอบอำนาจให้ประเมินแทนอย่างชัดเจน (ต้องระบุป้ายกำกับ
  ในเอกสารตามขั้นตอน 5)
- ห้ามถามคำถามที่ไม่มีตัวเลือกอย่างน้อย 3 แนวทางพร้อมข้อดีข้อเสีย เมื่อสิ่งใด
  ไม่ชัดเจน (ยกเว้นคำถามยืนยัน yes/no ล้วนๆ ที่ไม่มีทางเลือกเชิงออกแบบจริง)
- ห้ามเขียน section data flow โดยไม่อ้างอิง `user-journey.md` จริง (ห้ามคิด
  flow ขึ้นใหม่เองที่ไม่มีอยู่ในเอกสารต้นทาง) ถ้า user-journey.md ยังไม่มี
  ต้องแนะนำให้รัน `gen-feature-journey` ก่อนแล้วหยุดรอ
- ห้ามข้ามขั้นตอนแสดงผลให้ review ก่อนเขียนไฟล์ (ขั้นตอน 7) แม้ user จะรีบ
- ห้ามเขียนทับหรือลบ section ที่มีสถานะ `Confirmed` อยู่แล้วโดยไม่ถาม user
  ก่อน (ถ้าล้าสมัยจริงให้แนะนำย้ายไป `docs/00-archived/` แทน)
- ห้ามแก้ §3 ของ `Projexa-System-Design-R1.md` โดยไม่ผ่านขั้นตอน 8 (ถามและ
  ได้รับมติชัดเจนก่อนเสมอ)
