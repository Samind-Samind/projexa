# Build Prototype

Skill นี้คุมขั้นตอนสร้าง **ต้นแบบหน้าตาของระบบ (UI/UX Prototype)** แบบ static
HTML/CSS ต่อหน้าจอ ลงใน `docs/02-design/01-prototypes/vN/` โดยดึงข้อมูลจาก
เอกสาร 4 ชุดที่มีอยู่แล้วในโปรเจกต์ — spec รายหน้าจอ (`01-requirements/01-spec/`),
`backlog.md`, `feature-list.md`, `user-journey.md` — และควบคุมหน้าตาด้วย
`DESIGN.md` ตามหลัก **Human-in-the-loop** ของ Projexa (ดู `CLAUDE.md`): ไม่มี
เวอร์ชัน/ไฟล์ใดถูกสร้างหรือเขียนทับโดยไม่ผ่านการยืนยันจาก user ก่อน

**สำคัญ:** ทำขั้นตอนที่ 1–6 ด้านล่างเองใน main loop (ห้ามส่งให้ sub agent ทำ)
เพราะต้องถาม-ตอบและขอยืนยันกับ user แบบ interactive ส่วน "การเขียนไฟล์จริง"
(สร้าง/แก้ HTML, DESIGN.md, `_meta.md`, index, log) ให้มอบหมายให้ sub agent
ชื่อ `prototype-builder` ผ่าน Agent tool เมื่อทุกอย่างถูกยืนยันแล้วเท่านั้น
sub agent ตัวนี้ทำงานแบบ one-shot และถามคำถามกลับ user ไม่ได้

## ขั้นตอน

### 1. รับสโคปที่จะสร้าง prototype

ถ้า user ระบุมาแล้วในข้อความ (เช่น รหัส SCR, ชื่อหน้าจอ, โมดูล M1–M7, หรือ
"ทั้งหมด") ให้ resolve เป็นรายชื่อ SCR code ที่ชัดเจนโดยเทียบกับ
`backlog.md`/`feature-list.md` ถ้า **ไม่ได้ระบุ** ต้องถามด้วย
`AskUserQuestion` เสมอ พร้อมตัวเลือกอย่างน้อย 3 แนวทาง เช่น:

- ตัวเลือก 1: ทั้งหมด 26 หน้าจอ (ครบทุกโมดูล M1–M7) — ข้อดี: เห็นภาพระบบเต็ม
  ใช้สื่อสารกับผู้บริหาร/ผู้มีส่วนได้ส่วนเสียได้ครบ ข้อเสีย: ใช้เวลาสร้าง/
  รีวิวมาก และหลายหน้าจอยังเป็น Phase 2 ที่ยังไม่แน่ใจ
- ตัวเลือก 2: เฉพาะ MVP RAISE (13 หน้าจอ ตาม
  `Projexa-System-Design-R1.md` §10) — ข้อดี: ตรงกับขอบเขตที่จะพัฒนาจริงก่อน
  ทำเร็วกว่า ข้อเสีย: ไม่เห็นภาพรวมทั้งระบบ อาจต้องทำเพิ่มทีหลังสำหรับ
  Phase 2
- ตัวเลือก 3: ระบุเจาะจงเอง (พิมพ์รหัส SCR หรือชื่อโมดูล) — ข้อดี: ตรงความ
  ต้องการเฉพาะจุดที่สุด ข้อเสีย: ต้องรู้ scope ที่ต้องการล่วงหน้า

ถ้า user เลือกแก้ไข/เพิ่มจากเวอร์ชันเดิมที่มีอยู่แล้ว ให้ยึด scope เดิมของ
เวอร์ชันนั้นเป็นฐาน แล้วถามเฉพาะส่วนที่เปลี่ยน (เพิ่มหน้าจอใหม่ / แก้หน้าจอที่
มีอยู่ / ทั้งสองอย่าง)

### 2. ตรวจไฟล์ต้นทางให้ครบก่อนเริ่ม

ตรวจด้วย `Glob`/`Read` มิฉะนั้นแจ้ง user และหยุด:

- `docs/01-requirements/backlog.md`
- `docs/01-requirements/feature-list.md`
- `docs/02-design/01-prototypes/user-journey.md`
- ไฟล์ spec ใน `docs/01-requirements/01-spec/` ของ**ทุก** SCR ในสโคปที่เลือก

ถ้าไฟล์ระดับสรุป (`feature-list.md`/`user-journey.md`) ขาด ให้แนะนำ user รัน
skill `gen-feature-journey` ก่อน ถ้าไฟล์ spec รายหน้าจอขาด ให้แนะนำ skill
`requirement` ก่อน — ถามด้วย `AskUserQuestion` ว่าจะ (ก) รอสร้างเอกสารที่ขาด
ก่อน หรือ (ข) ตัดหน้าจอนั้นออกจากสโคปแล้วทำต่อเฉพาะที่มีข้อมูลครบ

### 3. ตรวจ Design System (`DESIGN.md`)

- `Glob` หา `docs/02-design/01-prototypes/DESIGN.md`
- **ถ้ามีอยู่แล้ว** ให้ `Read` ผ่านๆ เพื่อรู้ธีม/token ปัจจุบัน ไม่ต้องถามอะไร
  เพิ่ม ข้ามไปขั้นตอน 4
- **ถ้าไม่มี** ต้องอธิบายให้ user เข้าใจว่า prototype ทุกหน้าจอต้องอ้างอิง
  Design System เพื่อให้หน้าตาสม่ำเสมอทั้งระบบ (ตามหลัก Template compliance/
  Structured ใน CLAUDE.md) แล้วถามด้วย `AskUserQuestion` เป็นชุดคำถาม (แต่ละ
  ข้อมีตัวเลือกอย่างน้อย 3 แนวทางพร้อมข้อดี/ข้อเสีย):
  1. **โทนสีที่ต้องการ** เช่น Earth tone + Minimalist (สงบ, อ่านง่าย,
     เหมาะงานราชการ/องค์กร แต่ดูธรรมดา) / Corporate blue-navy (น่าเชื่อถือ,
     คุ้นเคยกับซอฟต์แวร์องค์กรทั่วไป แต่ไม่มีเอกลักษณ์) / Modern vibrant
     accent (จดจำง่าย ดึงความสนใจ แต่เสี่ยงดูไม่เป็นมืออาชีพถ้าใช้กับงานเอกสาร
     ราชการ) / ระบุเองเป็นคำอธิบาย
  2. **สไตล์อ้างอิง** เช่น Flat minimalist (Muji-inspired) / Material-ish มี
     shadow บาง / เรียบทางการแบบ enterprise software ทั่วไป / ระบุเอง
  3. **โลโก้** ถามว่ามีไฟล์โลโก้จะส่งมาให้ใช้หรือไม่ ถ้ามีให้รับไฟล์แล้วบันทึก
     ไว้ใน `docs/02-design/01-prototypes/assets/` ถ้าไม่มี ให้ทำ prototype
     แบบไม่มีโลโก้ไปก่อน (wordmark ตัวอักษรล้วน) แล้วเพิ่มได้ทีหลัง
  - สรุปคำตอบทั้งหมดให้ user ยืนยันหนึ่งครั้ง ก่อนส่งให้ sub agent เขียน
    `DESIGN.md` พร้อมกับ prototype รอบนี้ในการเรียกเดียวกัน (ดูขั้นตอน 6)

### 4. ตรวจสอบเวอร์ชันที่มีอยู่

`Glob` `docs/02-design/01-prototypes/v*/` (เฉพาะโฟลเดอร์ระดับ `vN` ตรงๆ)

- **ไม่มีเวอร์ชันไหนเลย** → ใช้ `v1` ได้ทันที ไม่ต้องถาม (ไม่มีอะไรให้เลือก)
- **มีอยู่แล้ว** → `Read` ไฟล์ `_meta.md` ของเวอร์ชันเลขสูงสุด (ล่าสุด) เพื่อดู
  สถานะ (Draft ระหว่างพัฒนา / Reviewed / Confirmed) และสโคปเดิม แล้ว
  **ต้องถามผู้ใช้ทุกครั้งที่ skill นี้ถูกเรียกซ้ำ** ด้วย `AskUserQuestion` ว่า
  จะสร้างเวอร์ชันใหม่ `v{N+1}` หรือแก้ไข `v{N}` เดิม โดยจัดลำดับตัวเลือกที่
  แนะนำไว้เป็นตัวแรกเสมอ พร้อมเหตุผลตามเกณฑ์นี้:
  - แนะนำ **สร้างเวอร์ชันใหม่ `v{N+1}`** เมื่อ: เวอร์ชันล่าสุดมีสถานะ
    "Reviewed"/"Confirmed" แล้ว (ไม่ควรเขียนทับของที่ผู้มีส่วนได้ส่วนเสีย
    ยืนยันไปแล้ว), หรือรอบนี้มีการเปลี่ยนโครงสร้างมาก (เพิ่ม/ลดหน้าจอ,
    เปลี่ยน DESIGN.md token สำคัญ) — ข้อดี: เก็บประวัติเทียบก่อน-หลังได้
    ครบ ข้อเสีย: โฟลเดอร์เพิ่มขึ้น ต้องคอยอัปเดตลิงก์ล่าสุด
  - แนะนำ **แก้ไข `v{N}` เดิม** เมื่อ: เวอร์ชันล่าสุดยังเป็น Draft ที่ยังไม่ได้
    ส่งรีวิว หรือเป็นการแก้เล็กน้อย (fix ข้อความ, ปรับ layout เล็กน้อยที่ไม่
    กระทบโครงสร้าง) — ข้อดี: ไม่ทำให้เวอร์ชันบวมเกินจำเป็น ข้อเสีย: ถ้าเคย
    ส่งให้ใครดูไปแล้วจะเห็นหน้าตาเปลี่ยนโดยไม่มีร่องรอยเวอร์ชันก่อน

### 5. สรุปแผนให้ user ยืนยันก่อนเขียนไฟล์

ก่อนเรียก sub agent ให้สรุปสั้นๆ ว่าจะทำอะไร: รายชื่อ SCR ที่จะสร้าง/แก้,
ปลายทาง (`v{N}` ใหม่ หรือแก้ `v{N}` เดิม), จะเขียน `DESIGN.md` ใหม่หรือไม่ —
แล้วขอยืนยันหนึ่งครั้ง เพราะเป็นการสร้าง/แก้ไฟล์จริงในโปรเจกต์

### 6. มอบหมายให้ sub agent `prototype-builder`

เมื่อ user ยืนยันแล้ว เรียกผ่าน Agent tool (subagent_type: `prototype-builder`)
พร้อมข้อมูลทั้งหมดที่จำเป็นในพรอมป์:

- วันที่ปัจจุบัน (`YYYYMMDD` และ `YYYY-MM-DD`) จาก context ของ session —
  อย่าให้ sub agent เดาเอง
- โหมดของ DESIGN.md: "ใช้ของเดิม" หรือ "สร้างใหม่" (ถ้าสร้างใหม่ ส่งคำตอบที่
  ยืนยันแล้วทั้งหมดจากขั้นตอน 3: โทนสี, สไตล์, path โลโก้ถ้ามี)
- โฟลเดอร์เวอร์ชันปลายทางที่ resolve แล้ว (`v{N}` ตรงๆ ไม่ให้ sub agent เดา
  เลขเอง) และว่าเป็น "เวอร์ชันใหม่" หรือ "แก้เวอร์ชันเดิม"
- ถ้าแก้เวอร์ชันเดิม: สรุปว่าจะเพิ่มหน้าจอไหนใหม่ / แก้หน้าจอไหนที่มีอยู่
- รายชื่อ SCR ทั้งหมดในสโคป พร้อม path ไฟล์ spec ที่เกี่ยวข้องของแต่ละอัน
- สรุปการเปลี่ยนแปลงจากเวอร์ชันก่อนหน้า (ถ้ามีเวอร์ชันก่อน) สำหรับใส่ใน
  `_meta.md`

sub agent จะจัดการให้ครบ: (ถ้าสั่ง) เขียน `DESIGN.md`, สร้าง/แก้ HTML ต่อ
หน้าจอ, สร้าง/แก้ `index.html` ของเวอร์ชันนั้น, เขียน `_meta.md`, อัปเดต
`docs/02-design/01-prototypes/index.md`, และบันทึก `docs/05-log/`

### 7. รายงานผลกลับ user

สรุป path ไฟล์ที่ถูกสร้าง/แก้ไขทั้งหมด ย้ำว่าเป็น **Draft ที่ต้องรอ
SA/PM/Design Lead ยืนยัน** ตามหลัก Human-in-the-loop จากนั้นถาม (optional,
ไม่บังคับ) ว่า user ต้องการ:

- เปิดดู `index.html` ของเวอร์ชันนั้นใน Browser pane เลยไหม (ใช้
  `preview_start`/`navigate`), หรือ
- เผยแพร่เป็น Artifact เพื่อส่งลิงก์ให้ผู้มีส่วนได้ส่วนเสียรีวิวง่ายขึ้น (ต้อง
  โหลด skill `artifact-design` ก่อนใช้ Artifact tool เสมอตามข้อกำหนดของ
  Artifact tool เอง)

## สิ่งที่ห้ามทำ

- ห้ามให้ sub agent ตัดสินใจเรื่อง scope, เวอร์ชันใหม่/แก้เวอร์ชันเดิม, หรือ
  เนื้อหา `DESIGN.md` เอง — ทุกอย่างต้องถูกตัดสินและยืนยันโดย user ผ่าน main
  loop นี้ก่อนแล้วส่งเป็นค่าที่ finalize แล้วเท่านั้น
- ห้ามข้ามขั้นตอนตรวจไฟล์ต้นทาง (ขั้นตอน 2) แม้ user จะรีบ
- ห้ามเขียนทับโฟลเดอร์เวอร์ชันเดิมโดยไม่ถามก่อนตามขั้นตอน 4 แม้จะดูเหมือนเป็น
  การแก้เล็กน้อยก็ตาม
- ห้ามลบหรือย้ายโฟลเดอร์เวอร์ชันเก่าใดๆ ระหว่างทำงาน (ถ้าเวอร์ชันเก่าล้าสมัย
  จริง ให้แจ้ง user ว่าควรย้ายไป `docs/00-archived/` เอง ไม่ใช่หน้าที่ของ
  skill นี้ที่จะตัดสินใจ)
