# Requirement → Backlog

Skill นี้คุมขั้นตอนแปลง "requirement ดิบ" จาก user ให้กลายเป็นเอกสารข้อกำหนด
(`docs/01-requirements/01-spec/`) พร้อมอัปเดต backlog และ log ตามหลัก
**human-in-the-loop** ของ Projexa (ดู `CLAUDE.md`) — ไม่มีข้อมูลใดเข้าเอกสารโดย
ไม่ผ่านการยืนยันจาก user

**สำคัญ:** ทำขั้นตอนที่ 1–5 ด้านล่างเองใน main loop (ห้ามส่งให้ sub agent ทำ)
เพราะต้องถาม-ตอบกับ user แบบ interactive ส่วน "การเขียนไฟล์จริง" (สร้าง spec,
อัปเดต `backlog.md`, บันทึก log) ให้มอบหมายให้ sub agent ชื่อ
`requirement-writer` ผ่าน Agent tool เมื่อข้อมูลครบและ user ยืนยันแล้วเท่านั้น
sub agent ตัวนี้ทำงานแบบ one-shot และถามคำถามกลับ user ไม่ได้

## ขั้นตอน

### 1. รับ requirement ดิบ

ถ้า user ยังไม่ได้เล่า requirement มาในข้อความ ให้ถามตรง ๆ ว่าต้องการ
requirement/feature อะไร รับเป็นข้อความอิสระ (ภาษาไทยหรืออังกฤษก็ได้) ไม่ต้อง
บีบให้เข้ารูปแบบใด ๆ ในขั้นนี้

### 2. ตรวจสอบเอกสารเดิมที่เกี่ยวข้อง

- `Glob` `docs/01-requirements/01-spec/*.md` และอ่าน
  `docs/01-requirements/backlog.md` (ถ้ามี) เพื่อดูว่ามี requirement ที่
  ใกล้เคียง/ทับซ้อน/เป็น scope เดียวกันอยู่แล้วหรือไม่
- ถ้า user เอ่ยถึงเอกสาร requirement เดิม (อ้าง path, ชื่อเรื่อง, หรือเลข
  running) ให้เปิดอ่านเอกสารนั้นก่อนตัดสินใจ
- วิเคราะห์ว่าเนื้อหาที่ได้มาควร:
  - (ก) **สร้างเอกสารใหม่** — เป็นความต้องการที่แยกจากเดิมชัดเจน
  - (ข) **แก้ไข/เพิ่มเติมเอกสารเดิม** — เป็นรายละเอียดเพิ่มของ requirement
    ที่มีอยู่แล้ว (เช่น เพิ่ม acceptance criteria, ขยาย scope เดิม)
  - ถ้าไม่ชัดเจนระหว่าง (ก)/(ข) ให้ถาม user ในขั้นตอนที่ 3 ด้วยตัวเลือก
    ที่ระบุเอกสารเดิมที่เกี่ยวข้องให้ชัดเจน

### 3. ถามเมื่อไม่แน่ใจ

ทุกครั้งที่ไม่แน่ใจในส่วนใดของ requirement (ขอบเขต, ผู้ใช้งานเป้าหมาย,
ความสำคัญ/priority, ว่าเป็นเอกสารใหม่หรือแก้เอกสารเดิม, acceptance criteria
ฯลฯ) **ต้องถาม user ด้วย `AskUserQuestion`** และ **ต้องมีตัวเลือกให้เลือก
อย่างน้อย 3 แนวทางเสมอ** (ไม่ใช่แค่ yes/no) เช่น:

> "requirement นี้ควรรวมกับเอกสาร `[[20260810-004-...]]` เดิม หรือแยกเป็น
> เอกสารใหม่?"
> - ตัวเลือก 1: รวมกับเอกสารเดิม (ขยาย scope)
> - ตัวเลือก 2: สร้างเอกสารใหม่ แต่ลิงก์อ้างอิงเอกสารเดิมไว้
> - ตัวเลือก 3: สร้างเอกสารใหม่ แบบไม่เกี่ยวข้องกับเอกสารเดิมเลย

ถามได้หลายรอบจนกว่าจะเก็บข้อมูลครบพอจะเขียนเอกสารได้ ไม่ต้องรีบสรุปถ้ายัง
มีความกำกวมสำคัญเหลืออยู่

### 4. สรุปให้ user ยืนยันก่อนเขียนไฟล์

ก่อนเรียก sub agent ให้สรุปให้ user เห็นภาพรวมสั้น ๆ ว่าจะสร้าง/แก้เอกสารอะไร
(หัวข้อ, ใหม่หรือแก้เอกสารเดิม, acceptance criteria ที่เก็บได้) แล้วขอ
ยืนยันหนึ่งครั้ง เพราะเป็นการสร้าง/แก้ไขไฟล์ในโปรเจกต์จริง

### 5. มอบหมายให้ sub agent `requirement-writer`

เมื่อ user ยืนยันแล้ว ให้เรียก sub agent ผ่าน Agent tool (subagent_type:
`requirement-writer`) พร้อมข้อมูลทั้งหมดที่จำเป็นในพรอมป์ ได้แก่:

- วันที่ปัจจุบัน (รูปแบบ `YYYYMMDD` และ `YYYY-MM-DD`) — ดึงจาก context ของ
  session (เช่น `currentDate`) อย่าให้ sub agent เดาเอง
- หัวข้อ/สรุปสั้นของ requirement (สำหรับใช้เป็นชื่อไฟล์)
- เนื้อหา requirement ที่ finalize แล้วทั้งหมด (raw requirement + รายละเอียด
  ที่ถาม-ตอบมา)
- ผลวิเคราะห์: สร้างเอกสารใหม่ หรือแก้เอกสารเดิม (พร้อม path เอกสารเดิมถ้ามี)
- อ้างอิง TOR clause/เอกสารอื่นที่เกี่ยวข้อง (ถ้ามี)
- acceptance criteria ที่เก็บได้
- ผู้ให้ requirement (ถ้าทราบ)

sub agent จะจัดการให้ครบทั้ง: เขียน/แก้ spec ใน `01-requirements/01-spec/`,
อัปเดต `01-requirements/backlog.md`, และบันทึก `05-log/(YYYYMMDD)-log.md`

### 6. รายงานผลกลับ user

สรุปให้ user เห็น path ของไฟล์ที่ถูกสร้าง/แก้ไขทั้งหมด (เอกสาร spec, backlog,
log) และ TODO ที่เหลือถ้า sub agent รายงานว่ามีข้อมูลไม่ครบ
