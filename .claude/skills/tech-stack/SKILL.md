# Tech Stack Selection & Documentation

Skill นี้คุมขั้นตอนช่วย **เลือกเทคโนโลยีที่เหมาะสม** และจัดทำ **เอกสารตัดสินใจ
tech stack** ของโปรเจกต์ Projexa ที่
`docs/02-design/02-technical/tech-stack.md` ครอบคลุมได้หลาย layer:
Frontend, Backend, Database, File Storage, Auth, AI Integration,
Hosting/Deployment

ตามหลัก **Human-in-the-loop** และ "ห้ามเดา" ของ Projexa: ทุกเกณฑ์/น้ำหนัก/
คะแนนที่ใช้ตัดสินใจต้องอิงข้อมูลจริงจากเอกสารโปรเจกต์หรือคำตอบของ user เท่านั้น
ถ้าข้อมูลที่จำเป็นต่อการให้คะแนนไม่มีอยู่จริง **ต้องถาม ห้ามสมมติเอง** และ
เอกสารผลลัพธ์**ไม่ใช่**มุมมองสรุปแบบ `feature-list.md`/`user-journey.md` —
ห้ามเขียนทับหัวข้อที่เคย Confirmed แล้วโดยไม่ถาม ถ้าล้าสมัยจริงให้แนะนำย้ายไป
`docs/00-archived/` แทนการลบ/ทับ

**สำคัญ:** ทำขั้นตอนที่ 1–9 ด้านล่างเองใน main loop (ห้ามส่งให้ sub agent ทำ)
เพราะต้องสัมภาษณ์-วิเคราะห์-ขอยืนยันกับ user แบบ interactive ส่วน "การเขียน
ไฟล์จริง" ให้มอบหมายให้ sub agent ชื่อ `tech-stack-writer` ผ่าน Agent tool
เมื่อทุกอย่างถูกวิเคราะห์และยืนยันแล้วเท่านั้น sub agent ตัวนี้ทำงานแบบ
one-shot และถามคำถามกลับ user ไม่ได้ — **ห้ามให้ sub agent เป็นคนให้คะแนนหรือ
ตัดสินใจเทคโนโลยีเอง** หน้าที่นั้นเป็นของขั้นตอนในสกิลนี้เท่านั้น

## ขั้นตอน

### 1. รับสโคป (layer ที่จะทำ)

ถ้า user ระบุมาแล้ว (เช่น "เทียบ Database ให้หน่อย", "เลือก Frontend/Backend
ใหม่") ให้ resolve เป็นชุด layer ที่ต้องทำ ถ้า **ไม่ได้ระบุ** ให้ถามด้วย
`AskUserQuestion` (multiSelect) อย่างน้อย 3 ตัวเลือก เช่น:

- ตัวเลือก 1: เฉพาะ layer ที่ยังไม่เคยเปรียบเทียบ/ตัดสินใจอย่างเป็นทางการ —
  ข้อดี: เร็ว ไม่ถามซ้ำสิ่งที่ยืนยันแล้ว ข้อเสีย: อาจพลาดโอกาสทบทวนของเดิมถ้า
  บริบทเปลี่ยนไปมาก
- ตัวเลือก 2: ทบทวนใหม่ทั้งหมดทุก layer รวมที่เคยตัดสินใจไปแล้ว — ข้อดี: ได้
  ข้อสรุปที่สอดคล้องกันทั้งระบบ ข้อเสีย: ใช้เวลาสัมภาษณ์นานกว่า
- ตัวเลือก 3: ระบุเจาะจงเอง (พิมพ์ชื่อ layer)

### 2. ตรวจเอกสารตัดสินใจเดิม

`Glob`/`Read` `docs/02-design/02-technical/tech-stack.md` ถ้ามีอยู่แล้ว: อ่าน
เพื่อรู้ว่า layer ไหน**สถานะ Confirmed**แล้ว (มีวันที่ยืนยัน) กับ layer ไหนยัง
`Draft`/ยังไม่มี — ใช้กำหนดว่าขั้นตอน 5 ต้องถามอะไรเพิ่ม **ห้ามถามซ้ำสิ่งที่
Confirmed แล้ว** เว้นแต่ user เลือกตัวเลือก 2 ในขั้นตอน 1 (ทบทวนใหม่ทั้งหมด)
โดยชัดเจน

ถ้าในบทสนทนานี้เอง**มีข้อมูลบริบท/ผลวิเคราะห์อยู่แล้ว** (เช่น เพิ่งเปรียบเทียบ
Frontend/Backend กันมาก่อนหน้าข้อความล่าสุด) ให้ใช้ข้อมูลเดิมได้เลยไม่ต้อง
สัมภาษณ์ซ้ำ ถามเฉพาะส่วนที่ยังขาดหรือยังไม่ชัดพอจะเขียนเป็นเอกสารทางการได้

### 4. สรุปข้อเท็จจริง vs ช่องว่างที่ต้องถาม

รวบรวมจากขั้นตอน 3 แล้วแยกให้ชัดต่อหัวข้อว่า **มีข้อมูลจริงจากเอกสารแล้ว**
หรือ **NOT DOCUMENTED** (ห้ามเดาแทนช่องที่ไม่มีข้อมูล) หัวข้อที่ต้องเช็คเสมอ
(เลือกเฉพาะที่เกี่ยวกับ layer ในสโคป):

- โหมดพัฒนา: ทีมถนัดเทคโนโลยีใดจริง หรือให้ AI coding agent เขียนโค้ดเป็นหลัก
- Deployment/Hosting target: cloud provider / on-prem / งบต่ำ-free tier, และ
  data residency (PDPA ถ้าเก็บข้อมูลส่วนบุคคล)
- งบประมาณ/นโยบาย license (ต้อง open-source ล้วนหรือจ่ายค่า managed service
  ได้)
- Non-functional: จำนวนผู้ใช้พร้อมกันโดยประมาณ, ปริมาณข้อมูล/ไฟล์ที่คาดว่าจะ
  เก็บ, ความต้องการ uptime/SLA
- Integration ที่ต้องรองรับ: SSO/ระบบองค์กรเดิม, ช่องทางแจ้งเตือน (LINE/Email)
- ขอบเขตไฟล์ TOR ที่ต้องรองรับจริง (ถ้ากว้างกว่าที่ระบุใน SCR-004/§10 เช่น
  ไฟล์สแกน/รูปภาพ ต้องถามยืนยันแยกจากสโคปเดิม เพราะกระทบเกณฑ์ OCR/vision)
- Browser/Device matrix ที่ต้องรองรับจริง (ถ้า test-plan.md ยังเป็น
  `(suggested)`/TODO)
- ลำดับความสำคัญของเกณฑ์ให้คะแนน (ความเร็ว MVP / maintainability ระยะยาว /
  ต้นทุน-license / ให้ AI ประเมินแบบสมดุลเอง)
- ทีมงาน/timeline ที่ยืนยันจริง (ถ้าต่างจาก §12)

### 5. สัมภาษณ์ผู้ใช้แบบเข้มข้น

สำหรับทุกหัวข้อในขั้นตอน 4 ที่เป็น **NOT DOCUMENTED** และเกี่ยวกับ layer ใน
สโคป **ต้องถามด้วย `AskUserQuestion`** แบ่งเป็นชุดละไม่เกิน 4 คำถามต่อการเรียก
1 ครั้ง (เรียกได้หลายรอบจนครบ) **ทุกคำถามต้องมีตัวเลือกอย่างน้อย 3 แนวทางเสมอ
พร้อมข้อดี-ข้อเสียของแต่ละตัวเลือกในคำอธิบาย** (ไม่ใช่แค่ yes/no) ตัวอย่าง
รูปแบบ:

> "แผน deploy ระบบจะอยู่ที่ไหน?"
> - ตัวเลือก 1: Cloud provider หลัก (AWS/Azure/GCP) — ข้อดี: managed service
>   ครบ scale ง่าย ข้อเสีย: ค่าใช้จ่ายสูงกว่าถ้าโหลดน้อย
> - ตัวเลือก 2: On-prem/server องค์กร — ข้อดี: คุม data residency ได้เอง
>   ข้อเสีย: ต้องดูแล infra เอง
> - ตัวเลือก 3: Cloud ต้นทุนต่ำ/free-tier — ข้อดี: เหมาะ MVP งบจำกัด ข้อเสีย:
>   อาจต้อง migrate ตอนสเกล

ถ้า user ตอบแบบเปิดกว้าง/มอบให้ AI ตัดสินใจแทน (เช่น "ช่วยคิดให้หน่อย", "ให้ AI
ประเมินเอง") ให้บันทึกไว้ว่าเป็น**มติที่ user มอบอำนาจให้ประเมินแทน** (ไม่ใช่
ข้อมูลจริงจาก user) แล้วใช้เป็นน้ำหนัก/สมมติฐานในขั้นตอนถัดไปได้ แต่ต้องระบุ
ป้าย `(ประเมินแทนโดย AI ตามที่ user มอบอำนาจ)` กำกับไว้ในเอกสารเสมอ — ไม่ใช่
การเดาแบบไม่มีที่มา

ถามได้หลายรอบจนกว่าจะเก็บข้อมูลครบพอจะให้คะแนนได้อย่างสมเหตุสมผล ไม่ต้องรีบสรุป
ถ้ายังมีความกำกวมสำคัญเหลืออยู่

### 6. กำหนดเกณฑ์และน้ำหนัก (Weighted Scoring Model)

สังเคราะห์จากคำตอบขั้นตอน 5 เป็นตารางเกณฑ์+น้ำหนัก+เหตุผล (แสดงให้ user เห็น
ก่อนเริ่มให้คะแนนจริง) ถ้าเกณฑ์/น้ำหนักมีผลกระทบมาก และ user ยังไม่ได้ระบุลำดับ
ความสำคัญชัดเจนในขั้นตอน 5 ให้ถามยืนยันอีกครั้งด้วย `AskUserQuestion` ก่อน
เริ่มให้คะแนน

### 7. เปรียบเทียบตัวเลือกด้วย Weighted Scoring Model / Trade-off Matrix

สำหรับแต่ละ layer ในสโคป:

- เสนอ**อย่างน้อย 5 ตัวเลือกเทคโนโลยี** ที่สมเหตุสมผลสำหรับโปรเจกต์นี้จริง
  (ยกเว้นกรณีมี hard requirement จากเอกสาร §4/§11 ที่ตัดตัวเลือกอื่นออกจนไม่
  เหลือ 5 ทางที่สมเหตุสมผล เช่น JSONB requirement ของ Database — กรณีนี้ให้
  ระบุเหตุผลตรงๆ แทนตาราง 5 ตัวเลือก)
- ให้คะแนนตามเกณฑ์ในขั้นตอน 6 ทำตารางคะแนนรวม (weighted sum)
- สรุปข้อดี/ข้อเสียย่อของแต่ละตัวเลือก
- ถ้า `Projexa-System-Design-R1.md` §11 มีข้อเสนอเดิมสำหรับ layer นี้อยู่แล้ว
  ให้เทียบว่า**เหมือนหรือต่างกับผลวิเคราะห์รอบนี้** พร้อมเหตุผล (ถ้าต่างกัน
  ต้องเสนอแนวทางอย่างน้อย 3 ทางให้ user เลือกว่าจะจัดการความต่างนี้อย่างไร
  เช่น ยึดผลวิเคราะห์ใหม่/คงของเดิม/รอข้อมูลเพิ่มก่อนตัดสิน)

### 8. แสดงผลให้ user รีวิวก่อนเขียนไฟล์เสมอ

**ห้ามเรียก sub agent ก่อนขั้นตอนนี้เด็ดขาด** แสดงตาราง Weighted Scoring
+ข้อดีข้อเสีย+คำแนะนำของทุก layer ในสโคปให้ user เห็นในแชทก่อน แล้วขอให้ user
ยืนยันการตัดสินใจต่อ layer อย่างชัดเจน (เช่น "ยืนยันตามคำแนะนำ" หรือ "เลือก
ตัวเลือกอื่นแทน" หรือ "ขอข้อมูลเพิ่มก่อนตัดสิน") — layer ที่ user ยังไม่ยืนยัน
ให้คงสถานะ `Draft (suggested)` ในเอกสาร ไม่ใช่ `Confirmed`

### 9. ถามเรื่อง sync กับ §11 ของ Projexa-System-Design-R1.md

ถ้ามี layer ที่ผลตัดสินใจรอบนี้ต่างจากตาราง §11 เดิม **ต้องถาม**ด้วย
`AskUserQuestion` อย่างน้อย 3 ตัวเลือก เช่น:

- ตัวเลือก 1: แก้ตาราง §11 ให้ตรงกับผลตัดสินใจใหม่ + ใส่ note อ้างอิงไปที่
  `tech-stack.md` เป็น source of truth — ข้อดี: ไม่มีข้อมูลขัดแย้งกันใน repo
  ข้อเสีย: ต้องแก้เอกสารหลักของระบบ
- ตัวเลือก 2: ไม่แก้ §11 ให้ `tech-stack.md` เป็นเอกสารล่าสุดเพียงจุดเดียว
  พร้อมลิงก์ไขว้ทั้งสองทาง — ข้อดี: ไม่กระทบเอกสารหลัก ข้อเสีย: มีข้อมูล 2
  เวอร์ชันอยู่ใน repo ต้องดูวันที่ให้ดี
- ตัวเลือก 3: ยังไม่ตัดสินใจตอนนี้ รอ PM/SA ยืนยันเป็นทางการก่อนค่อย sync

### 10. สรุปแผนให้ user ยืนยันครั้งสุดท้าย

สรุปสั้นๆ ว่าจะสร้าง/แก้ไฟล์อะไรบ้าง (สร้างใหม่/แก้ layer section ใดใน
`tech-stack.md`, จะแก้ §11 หรือไม่) แล้วขอยืนยันหนึ่งครั้งก่อนเรียก sub agent
เพราะเป็นการสร้าง/แก้ไฟล์จริงในโปรเจกต์

### 11. มอบหมายให้ sub agent `tech-stack-writer`

เมื่อ user ยืนยันแล้ว เรียกผ่าน Agent tool (subagent_type:
`tech-stack-writer`) พร้อมข้อมูลทั้งหมดที่จำเป็นในพรอมป์ (ทุกอย่างต้อง
finalize แล้ว ห้ามส่งให้ sub agent ไปคิดต่อเอง):

- วันที่ปัจจุบัน (`YYYYMMDD` และ `YYYY-MM-DD`) จาก context ของ session
- โหมด: "สร้างใหม่ทั้งไฟล์" หรือ "แก้/เพิ่ม section ของ layer: {รายชื่อ}"
- บริบท/ข้อจำกัดที่สัมภาษณ์ได้ (พร้อมระบุอันไหนเป็นข้อมูลจริงจาก user อันไหน
  เป็น "ประเมินแทนโดย AI ตามที่ user มอบอำนาจ")
- เกณฑ์+น้ำหนักที่ใช้ พร้อมเหตุผล
- ต่อแต่ละ layer: ตารางคะแนนพร้อมตัวเลข, ข้อดี/ข้อเสียแต่ละตัวเลือก,
  คำแนะนำ, สถานะ (`Confirmed` พร้อมวันที่ / `Draft (suggested)`), ผลเทียบกับ
  §11 เดิมถ้ามี
- มติเรื่อง sync §11 จากขั้นตอน 9 (sync / ไม่ sync / รอ) — ถ้า sync ต้องระบุ
  ให้ชัดว่าแก้แถวไหนในตาราง §11 เป็นค่าอะไร

sub agent จะจัดการให้ครบ: เขียน/แก้ `docs/02-design/02-technical/tech-stack.md`,
อัปเดต `docs/02-design/02-technical/index.md`, แก้ §11 ของ
`Projexa-System-Design-R1.md` เฉพาะกรณีมีมติให้ sync, และบันทึก `docs/05-log/`

### 12. รายงานผลกลับ user

สรุป path ไฟล์ที่ถูกสร้าง/แก้ไขทั้งหมด, layer ไหน `Confirmed` แล้วบ้าง, layer
ไหนยัง `Draft (suggested)` รอข้อมูล/การยืนยันเพิ่ม, และย้ำว่าเอกสารนี้ต้องรอ
PM/SA ยืนยันเป็นทางการตามหลัก Human-in-the-loop ก่อนถือเป็นมติสุดท้ายของทีม

## สิ่งที่ห้ามทำ

- ห้ามให้ sub agent ตัดสินใจ ให้คะแนน หรือกำหนดเกณฑ์/น้ำหนักเทคโนโลยีเอง —
  ทุกอย่างต้องวิเคราะห์และยืนยันโดย user ผ่าน main loop นี้ก่อน แล้วส่งเป็น
  ค่าที่ finalize แล้วเท่านั้น
- ห้ามเดาคำตอบแทน user เมื่อเอกสารโปรเจกต์ไม่มีข้อมูล (`NOT DOCUMENTED`) —
  ต้องถามเสมอ ยกเว้น user มอบอำนาจให้ประเมินแทนอย่างชัดเจน (ต้องระบุป้ายกำกับ
  ในเอกสารตามขั้นตอน 5)
- ห้ามถามคำถามที่ไม่มีตัวเลือกอย่างน้อย 3 แนวทางพร้อมข้อดีข้อเสีย เมื่อสิ่งใด
  ไม่ชัดเจน (ยกเว้นคำถามยืนยัน yes/no ล้วนๆ ที่ไม่มีทางเลือกเชิงเทคนิคจริง)
- ห้ามเสนอน้อยกว่า 5 ตัวเลือกเทคโนโลยีต่อ layer โดยไม่ระบุเหตุผลชัดเจนว่าทำไม
  ตัวเลือกอื่นถึงไม่สมเหตุสมผล (ดูขั้นตอน 7)
- ห้ามข้ามขั้นตอนแสดงผลให้ review ก่อนเขียนไฟล์ (ขั้นตอน 8) แม้ user จะรีบ
- ห้ามเขียนทับหรือลบ layer section ที่มีสถานะ `Confirmed` อยู่แล้วโดยไม่ถาม
  user ก่อน (ถ้าล้าสมัยจริงให้แนะนำย้ายไป `docs/00-archived/` แทน)
- ห้ามแก้ §11 ของ `Projexa-System-Design-R1.md` โดยไม่ผ่านขั้นตอน 9 (ถามและ
  ได้รับมติชัดเจนก่อนเสมอ)
